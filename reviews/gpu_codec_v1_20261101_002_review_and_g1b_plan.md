## 2 当前结果揭示的优化对象

当前基线已经把实际低比特码流留在 GPU，并保持 CPU 数值语义。因此，它适合用作后续优化的正确性与性能对照。

其主要可改善实现成本之一，是大量持久的 int64 索引与临时 word 数组。[源代码中的打包工作区](../results/gpu_codec_v1/gpu_codec_v1_20261101_002/code/src/gradient_comm_lab/torch_codec.py)预先构造逐字节和逐元素的索引、位移及中间结果，编码和解码又各有多个全长张量。

| N=4194304 的预分配 roundtrip | 名义 b4 | 名义 b8 |
|---|---:|---:|
| 原始 BF16 输入 | 8 MiB | 8 MiB |
| 完整紧凑包 | 2.78125 MiB | 4.78125 MiB |
| workspace | 542.75 MiB | 702.75 MiB |
| 标准正态中位延迟 | 10.147397 ms | 12.868778 ms |

这些是该 eager 实现的成本，不是量化算法必然需要的内存和时间。较小输入的 trace 显示了多算子链，支持减少发射次数的优化尝试；但 N=65536 的 trace 不足以证明 N=4194304 也主要受发射开销限制。大输入还涉及大量临时数据读写，需要相应尺寸的剖析。

接受测量不等于认定所有数值都很稳定：67/104 case 有 session 内噪声标记，140/520 case-session 的 IQR/median 超过 10%；771/10400 块偏离目标计时长度。数据均保留，计算正确。b8 大输入 roundtrip 的 session 中位数为 7.934–13.346 ms，即使会话内标记为否，跨会话波动仍明显。

## 3 G1b 的最小实现范围

目标是在相同输入、LUT、阈值、码流和 BF16 舍入条件下，减少工作区、设备数据读写及内核调用，并量化实际收益。默认使用已经验证的项目局部 CUDA 11.8/MSVC 19.38 工具链，不需要为本轮更换 PyTorch 或重新规划环境。

### 3.1 先完成直接打包与解包

- 实现真正的 5/9 位码流 GPU 读写，不在全局显存中物化 O(N) 的 int64 索引和位移表。
- 可由元素或输出字节的位置在寄存器中计算码偏移；选定唯一写入归属，避免字节写竞争。
- 每 256 个元素恰好对应整数个 payload 字节，可作为自然的分块边界。具体线程/block 组织由实现者选择并说明。
- 保留原码值范围、低位优先顺序、尾部规范和尺度布局。不要顺便改成严格 INT4/INT8、公共尺度或新码本。

这个中间模块先独立通过所有合法码值及边界测试。若保留为消融版本，另命名 `cuda_pack_only_repaired`；它不替代最终完整 codec。

### 3.2 再融合局部编码和解码

- 优先以现有 16 元素尺度组和 256 元素顶层组组织局部计算，让中间量尽量留在寄存器或共享内存。
- 编码必须包括尺度计算、LUT 区间搜索、显式阈值舍入、尺度编码和真实打包；解码包括解包、尺度恢复及反量化。
- 保持每一步 BF16 舍入、BF16 常数、严格小于比较、整数索引偏移与负零。减少 kernel 数不能以默默改变算术语义为代价。
- checked API 与 trusted 内核保持分离，错误状态必须明确；非法索引或数据不能先触发越界访问再依赖异常作为检查。
- 扩展使用调用者的 PyTorch 当前 CUDA stream，设备选择和缓冲生命周期必须正确。增加非默认 stream 的小型依赖/结果检查；不要用全设备同步掩盖 stream 错误。
- 不要求强行做成一个 kernel。最终以数值通过、真实工作区和 encode/decode/roundtrip 成本判断。

本轮仍不实现解码—跨 worker 累加—重编码、ring、动态位宽、LCG 状态推进或新训练；这些属于 G2。

## 4 必须保持与补强的正确性要求

继承 002 的全部 82 个输入、两种位宽、协议边界和 CPU 参照身份。新实现独立接受 CPU 包解码验证，同时与 CPU 码流对照；不能只比较新旧 GPU 的量化 MSE。

新实现需覆盖尾块、空输入、正负零、subnormal、最大尺度、所有码值、阈值 0/65536、非法包和中间/输出溢出。扩展中的输入、阈值和 LUT 仍不可被修改；新 ABI 的错误处理、stream 与边界访问也要检查。

本次有一项非阻断测试改进：002 的预期拒绝助手允许较宽的异常类型集合，包含 RuntimeError。已记录的 60 次拒绝全部是具体且合理的 ValueError，因此没有发现当前假通过；但未来自定义内核的非法访问、OOM 或启动错误不能算“正确拒绝”。

**下一轮为每个非法输入用例固定预期的异常类型及消息/状态码。** 意料外的 CUDA 错误作为测试失败保留。测试助手修改应另存 diff/哈希，不能修改原参照输出、阈值或放宽数值容差。

新增或拆分测试允许改变记录数量；覆盖必须由用例清单核对，不把 1101 这个总数当作硬编码通过标准。

## 5 性能比较与噪声处理

### 5.1 必须在同一新 run 配对

比较 `torch_cuda_repaired` 和 `cuda_optimized_repaired`。旧 PyTorch 实现绑定 002 已验收源码哈希；仅可调整双实现测量 harness，不能悄悄改变旧基线的算法或计时边界。

先在少量开发 case 上验证构建、正确性和资源使用，再运行完整矩阵。最终沿用 104 case，每 case 两实现、5 session、每 session 20 块：若矩阵不变，原始计时应为 20800 条，逐方法汇总 208 条，显存记录 1040 条。

每个 case/session 内采用预先生成的平衡顺序交替测两实现，记录配对 block ID。各自完成预热并保证开始测量前没有待完成工作。不要先测完整个旧基线，再隔很久测新实现；也不要直接用 002 历史中位数作为新加速比的分母。

K 按 `(case_id,method_id)` 在正式测量前冻结。可改进 pilot，用实际 K 次调用的块长进行有限次调整，规则和次数上限在 pilot 前固定；不得挑最快观察或在正式数据出来后改 K。相同 K 不是配对的必要条件，比较各自 elapsed/K。

### 5.2 同时报告绝对成本与配对收益

按原格式报告每个实现的 GPU 时间、墙钟时间、session 内分位数、session 间范围、workspace 和总 device 存储。speedup 取同 session 的 PyTorch 中位数/优化版中位数，并展示各 session 的比值，不能只给最大加速比。

新增描述性字段 `session_median_max_over_min`，用于暴露会话内 noise_flag 未覆盖的慢漂移；不将该字段作为删数据条件。时钟、外部负载和 WDDM 状态继续记录。若结果差异小于波动，结论写不确定，允许在新 run 按预先说明的条件复测。

输入等效 GB/s 仍不是显存带宽或网络吞吐。保留预分配、包含分配、checked API 的独立边界；同一比较不得一边复用整个 plan，一边每次重新创建 plan。

### 5.3 至少覆盖一个小输入和一个大输入的 trace

建议对 N=65536 和 N=4194304 分别采集两实现的独立 GPU 活动；b4 必测，b8 若实现分支不同则也覆盖。保留实际活动类别、丢记录、时间窗与关联验证，CPU-only trace 仍标为缺少 GPU 活动。

trace 只用于理解调用、复制和设备执行，不替代无 profiler 的正式计时。先证明优化减少了哪些全局中间张量或调用，再讨论其与延迟变化的关系；不从一个小输入 trace 直接推广全部长度的主导瓶颈。

## 6 交付结果与通过条件

使用新的唯一 run 目录，引用 002 的输入及基线，不回写 002。沿用 REPORT、summary、契约、正确性 JSONL、raw/summary、memory、trace、源码和复现说明的交付结构。需要补充：

- 自定义 CUDA 源码、编译命令、实际加载的构建产物身份和公开接口。
- 逐用例预期拒绝规则及新增 stream 测试。
- 双方法、同 case/session 的配对记录及工作区组成。
- 至少小/大两种输入的剖析证据。
- 若有直接打包中间版本，说明它是开发/消融结果，最终主比较仍使用完整 codec。

完整 G1 的通过条件仍是：固定语义正确、覆盖齐全、测量有效、结果可复算。没有“必须快某个百分比”的验收门槛。优化无收益也可以形成合格结论；其后是否进入 G2 由成本与后续目标共同决定。

本轮可争取的履历成果是：实现保持逐位语义的 CUDA 低比特编解码，减少工作区并给出受控性能比较。相对该 PyTorch 基线的收益属于已测实现比较，不能自动写成优于现有先进 codec、完整 AllReduce 加速或大模型训练加速。
